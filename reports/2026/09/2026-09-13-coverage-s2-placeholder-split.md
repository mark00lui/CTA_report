## 1. ⚠⚠⚠ 先修正：是 8 檔，不是 19 檔

本系列的前兩份報告都寫了：

> `__` 同時代表兩種相反的知識狀態……**後者正是 ATR 那輪對 `invalidation` 做出的判定，涉及 19/39 檔**

**正確答案是 8 檔。**

錯誤的來源是我在做結構普查時寫的這一行：

```python
if isinstance(iv,(int,float)): inval_num+=1
else: inval_blank+=1          # ← 把「有文字條件」與「空」歸成同一類
```

`cta.invalidation` 的真實分布是**三類**不是兩類：

| 類別 | 檔數 | 例 |
|---|---:|---|
| 數值 | 20 | `invalidation: 1489.60` |
| **文字條件（有內容的判斷）** | **11** | MU：「週收盤跌破 804.25（MA120）→ 長多排列破壞。距現價 −17.53%」 |
| `__`（真正的空） | **8** | 3008／3131／3211／3533／3583／3661／3665／6187 |

⚠⚠ **更該記的不是算錯本身，是它為什麼躲過檢查。**

**2026-09-12 的收尾報告本來就寫對了** ——
它的 `sources` 明載「39 檔中 **8 檔**仍為 `__`（6187／3008／3665／3131／3661／3583／3211／3533，全部是台股）」。
**我跑了一次全清單普查、得到一個與既有結論矛盾的數字，然後沒有回頭對照那份已經算對的報告。**

**這與收尾報告裡記的「三次把序數結論下錯」是同一個形狀**：
可機械化的檢查跑了，**但跑的是錯的那一題** ——
「非數值」與「空」是兩個不同的問題，而我用前者的答案回答了後者。

→ **教訓寫進方法層**：普查的結果與既有報告牴觸時，**先假設普查錯了**。
既有報告是當時逐檔看過的，普查是一行 `isinstance`。

## 2. 拆開之後的語彙

| token | 意思 | 算不算缺口 |
|---|---|---|
| `__` | **不知道，去查** | **算** —— 它是一筆待辦 |
| `none_qualifies` | **已量化，結論是沒有東西合格** | **不算** —— 它是一個結論 |

### 驗收

| 條件 | 結果 |
|---|---|
| 8 檔全部改用新 token | ✓ 3008／3131／3211／3533／3583／3661／3665／6187 |
| 8 檔全部已有 `invalidation_basis` | ✓ 最短 3131 的 248 字元，最長 3665 的 1,020 字元 |
| `--gaps` 未填欄位數下降且差額等於遷移檔數 | ✓ **89 → 81，差額正好 8** |
| 六支腳本 0 block／0 error | ✓ |

⚠ 計畫報告寫的驗收條件是「下降量等於 19」——
**那個條件本身帶著第 1 節的錯誤，正確的驗收量是 8，而實測正是 8。**

### `validate_state.py` 新增的兩條規則

```python
if iv == MEASURED_NONE:
    if is_placeholder(basis):
        errors.append(... "「已量化且無位階合格」是一個結論，沒有依據就只是缺口換個寫法")
elif is_placeholder(iv):
    warns.append(... "若已用雙邊規則量化過且無位階合格，應改用 none_qualifies；否則這是尚未量化的真缺口")
```

**第一條是這一步的重點。** 一個沒有依據的 `none_qualifies`
比 `__` 更糟 —— 它宣稱查過了，但拿不出量到什麼。

## 3. token 在資料層，標籤在呈現層

`none_qualifies` 對讀 YAML 的人與腳本都清楚，但它不該原樣出現在公開站台上。
`build_site.py` 新增：

```js
function invalidationLabel(v) {
  if (v === 'none_qualifies')
    return '**無合格位階（已量化）** — 雙邊規則下沒有任何位階同時滿足「距現價 ≥2 倍 ATR」與「≤20%」。這是結論，不是尚未查證的缺口；依據見下方。';
  return v;
}
```

⚠ **反過來做（把 token 寫成一句中文存進 YAML）會同時失去兩邊**：
機器要用字串比對一句會被改寫的中文，而讀者看到的仍然是資料層的措辭。

## 4. 順帶修掉 S1 引入的一個回歸

S1 新增的 `COARSE` 區塊在預設輸出裡逐筆印 21 行，
**會把真正要看的 ERROR/WARN 洗掉** —— 這與 `.githooks/pre-commit` 對
`cross_check.py` 用 `--gate` 的理由完全相同（註解原文：
「F1–F7 有 27 檔會觸發，每次 commit 印一遍會洗掉真正要看的行」）。

改為預設只印一行摘要：

```
[COARSE] as-of 精度不足 21 筆（合法；陳舊判定取期間第一天）— 完整清單：python scripts/validate_state.py --stale
```

⚠ **一個把重要訊息淹掉的檢查，與一個靜默跳過的檢查，失效方式不同但後果相同。**
S1 修掉了後者，卻順手造了前者 —— 記在這裡。
