## 1. ⚠⚠⚠ 先修正前一份報告的一條驗證狀態

`reports/2026/09/2026-09-12-coverage-atr-round-closeout.md`（本報告取代者）的
`sources` 與 §14 記了：

> `validate_state.py --stale`（2026-09-12 執行）— 陳舊變數（>90 天）：**無**

**那句話是對的，但它覆蓋的不是全集合。**

`scripts/validate_state.py` 的相關兩段：

```python
def as_date(v):                                   # :49
    if is_placeholder(v):
        return None
    if isinstance(v, date):
        return v
    try:
        return datetime.strptime(str(v), "%Y-%m-%d").date()
    except ValueError:
        return None                               # ← 月精度、裸年份都掉到這裡

        u = as_date(kv.get("updated"))            # :141
        if u and (today - u).days > STALE_DAYS:   # ← None 不是報錯，是跳過
```

**回 `None` 之後沒有任何人抱怨。** 實測 `key_variables.updated` 的型別分布：

| 型別 | 筆數 | 對 `--stale` |
|---|---:|---|
| `date`（YAML 原生日期） | 189 | 看得見 |
| `str`（`__`、`2026-08`、`2026-05` …） | 32 | **靜默跳過** |
| `int`（`2024`、`2026`） | 6 | **靜默跳過** |
| `None` | 5 | **靜默跳過** |
| **合計** | **232** | **43 筆（18.5%）不可見** |

以寬鬆解析（`2026-08` → `2026-08-01`、`2026` → `2026-01-01`）補算，
43 筆裡有 21 筆解析得出日期，**其中 11 筆已逾 90 天門檻**：

腳本印出來的是一片空白，而空白讀起來像「都很新」。

**可機械化的檢查不要留給紀律；而一個會靜默跳過的檢查，比沒有檢查更危險，
因為它讓人以為查過了。**

## 2. 全清單量到的其餘結構缺陷

### 2.1 量級：散文對數值是 1,180 比 1

| | 數量 |
|---|---:|
| 全部字串欄位的字元總數 | 1,523,296 |
| 全部數值純量（int/float） | 1,292 |

問題不在散文多 —— 這是一個推論倉庫，散文本來就該多。
問題在於**「數字」這一類物件沒有被當成有型別的東西存**。

### 2.2 `value` 欄位有 22% 裝的不是值

`key_variables.value` 的型別：`float` 137／`int` 43／**`str` 52**（22%）。

最尖銳的一例是把時間序列塞進純量：

```yaml
- name: 營益率
  unit: '%'
  value: 16.70（2026Q2）；15.15（FY2025）；11.33（FY2024）    # 2308
```

**這是三筆 `(period, value)`，存成了一個字串。** 它永遠無法被比較、檢查或畫圖。

### 2.3 `unit` 是自由文字，而且夾帶了 as-of

232 個變數用了 **108 種相異的 `unit`**。其中不少把期間寫進單位裡：
`%（2026 Q2）`、`x (FY2027)`、`%（capex／營收）`、`%（2026 H1；去年同期 83）`。

**期間該有自己的欄位。** 單位與期間混在一格，兩者都無法被驗證。

### 2.4 型別混用

`monthly_revenue.yoy`：字串 21 筆、浮點 120 筆。

## 3. ⚠⚠ `__` 同時代表兩種相反的知識狀態

| 用法 | 意思 | 出處 |
|---|---|---|
| `gaps` 裡的 `__` | **不知道，去查** | 建檔規則：「未知填 `__` 並列進 `gaps`」 |
| `invalidation` 的 `__` | **已量化，結論是沒有位階合格** | ATR 那輪的雙邊規則判定，涉及 **19/39 檔** |

後者在前一份報告裡被明確定性為「**一個被量化的結論不是資料缺口**」，
**但它在檔案裡跟真正的缺口長得一模一樣。**

後果是可量的：`validate_state.py --gaps` 的統計會把這 19 個結論算成 19 個缺口，
於是「缺口變多」與「查證做得更徹底」在輸出上不可分辨。

## 5. 六步計畫與驗收條件

每一步都是：**改 → 跑六支驗證 → 寫一份報告 → 單獨 commit**。
順序依「先讓檢查看得見，再動資料的形狀，最後才做衍生層」排定。

| 步 | 內容 | 驗收條件 |
|---|---|---|
| **S1** | `as_date` 嚴格化：無法解析成日期的 `updated` 改為 **error**（不再靜默跳過），並修掉那 43 筆 | 六支腳本 0 block／0 error；`--stale` 的覆蓋率自 189/232 變成 232/232；第 1 節那 11 筆全部現形 |
| **S2** | 拆 `__` 的語義：為「已量化的空」引入獨立表示法，`--gaps` 不再把它算成缺口 | 19 檔的 `invalidation` 全部改用新表示法；`--gaps` 的缺口數下降且下降量等於 19 |
| **S3** | `key_variables` 型別化：`value` 收數值、期間移入 `period`、`unit` 收斂為受控詞彙；時間序列改存 list | 52 筆散文值歸位；`unit` 相異值大幅下降；`build_site.py` 輸出仍可再生 |
| **S4** | 把 `weighted_tp ↔ 最新報告 tp_after` 併入 `cross_check.py` 並納入閘門 | 新增檢查在現況下 39/39 通過；故意改壞一檔可被擋下 |
| **S5** | `event_log[].delta` 與 `signal.basis` 的歷史段搬進 `reports/` 沿革檔 | 原文一字不改；state 只留當下判斷；每檔一個 commit |
| **S6** | `scripts/build_db.py` 產生唯讀衍生索引（不進 git） | 與 `build_index`／`build_site` 同規格：單向產生、輸出被手改會被覆蓋 |

⚠ **S5 的量體是 433,201 字元，佔 state 檔字元數中位 23.8%（最高 MU 30.1%）。**
**它就是 CLAUDE.md 已經為 `coverage.yaml` 的 `equal_weight_factor_mix[].note` 認定過的
那個 prepend-only append-log 反模式 —— 只是它在 39 檔裡各複製了一份，而沒有人注意到。**
當初對 `coverage.yaml` 的結論是「搬到 `reports/`，因為只有那裡機械不可改」，
**同一個結論原封不動適用於此。**

## 6. 不做什麼

- **不改任何標的的情境、倍數、機率、目標價。** 這一輪是結構，不是判斷。
- **不把推論散文換成 markdown database。** 現有的 `reports/` 已經有 append-only 的
  機械強制與 git blame 的可追溯性；換成 front-matter 查詢語法是拿掉強制、換來語法，是淨損。
  要的是**在不動來源真相的前提下加一層可再生的衍生索引**（S6）。
- **不 push。**
