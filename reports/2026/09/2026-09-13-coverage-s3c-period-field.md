# coverage —— S3c：period 欄位，以及一個分類器算錯的數字

> 本文為公開研究記錄，非投資建議。作者不揭露任何持倉資訊，

**等級 L2**｜觸發：結構調整 S3c
**本報告不動任何標的的情境、倍數、機率或目標價。**

---

## 1. `period` 與 `updated` 是兩件事

| 欄位 | 問的是 |
|---|---|
| `updated` | **這一格何時被寫進 state**（S1 已嚴格化） |
| `period` | **這個數字描述的是哪一段時間** |

**因為 `period` 沒有欄位，它被夾帶進 `unit` 字串裡：**

```yaml
unit: '%（2026 Q2）'
unit: 億元新台幣（2026-07）
unit: x (FY2027)
```

**單位與期間混在一格，兩者都無法被驗證。**

拆開之後：

```yaml
- name: 毛利率
  kind: 量化
  value: 35.64
  unit: '%'             # 只放單位
  period: 2026 Q2       # 期間有自己的欄位
  updated: 2026-09-10   # 這一格何時被寫進 state
```

---

## 2. ⚠⚠ 只拆 14 筆是刻意的

`unit` 含括號者共 **95 筆**，但括號裡裝的是**三種不同的東西**：

| 類別 | 筆數 | 例 | 可否機械拆 |
|---|---:|---|---|
| 純期間 | **14** | `%（2026 Q2）`、`x (FY2027)` | ✓ 本步已拆 |
| **口徑註記** | — | `%（capex／營收）`、`%（樹林、錦興、昆山三廠平均）`、`%（非 GAAP，Q4 FY2026）` | ✗ |
| **額外數據** | — | `%（Q2 2026；Q1 約 29.5%）`、`%（2026 H1；去年同期約 83.7%）` | ✗ **那些其實是 `series` 的點** |

後兩類合計 **81 筆**。

**逐筆都要判斷，而機械拆會犯下 S3b 明文警告過的那個錯：把數字摘要掉。**
`%（Q2 2026；Q1 約 29.5%）` 若只取「Q2 2026」當 period，
**「Q1 約 29.5%」這個數字就消失了** —— 它其實應該變成 `series` 的第二點。

`validate_state.py` 每次執行印出剩餘筆數，讓它是一個**會縮小的數字**：

```
[UNIT] unit 仍夾帶期間或口徑 81 筆（純期間者已於 2026-09-13 拆入 period；
       其餘混著口徑與額外數據，逐筆都要判斷）
```

## 3. ⚠⚠ 修正我自己在規劃時算的一個數：是 81 不是 78

規劃時我寫「78 筆需逐筆判斷」。**正確是 81 筆。**

成因是分類用的正則要求括號必須在**字串結尾**：

```python
re.match(r'^(.*?)[（(](.+?)[）)]$', u)      # ← 結尾的 $
```

而有 **3 筆的括號在字串中間**，後面還接著別的東西：

```
INTU  USD bn（FY2026 扣 SBC 且扣一次性稅利益後的乾淨值）；FY2027 指引推算 6.581
MSFT  USD bn（TTM）；FCF 殖利率 1.82%、P/FCF 55.02x
2308  TWD（FactSet 中位數）；平均 60.06、高 80.91、低 41.08 → 全距 1.97 倍；23 位
```

**它們被誤歸為「無括號」。**

⚠ **這與 S2 那次「19 檔 vs 8 檔」是同一種錯：分類器問的題目和我以為它問的不一樣。**

差別在於**這次被抓到了**：遷移後我用第二個口徑（`含任何括號`）複核總數，
得到 14 + 81 = 95，與第一次普查的「含括號 95 筆」對得上，
而與「14 + 78 = 92」對不上。**那個複核本身是因為 S2 的教訓才做的。**

→ **方法層記一條：任何分類統計都要用第二個口徑複核總數。**
一個分類器不會告訴你它漏掉了什麼，只有總數對不上才會。

## 4. 衍生索引同步

`build_db.py` 的 `key_variables` 表新增 `period` 欄：

```sql
SELECT ticker, name, unit, period FROM key_variables WHERE period IS NOT NULL;
```
