# CTA 增量研究流程

## 核心設計

每支個股的**狀態（state）**存在 `state/<ticker>.yaml`，那是唯一真實來源。使用者每次只提供**事件（event）**，你的工作是產生**差分（delta）**：

```
state(t) + event → 影響掃描 → 定級(L0–L3) → 依級修正 → 變更單 + state(t+1)
```

不重建整份報告。重建 context 是成本，不是價值。

## 資料來源層級

推論的品質上限由資料的家決定。同一個數字散在兩個地方，你會有兩個版本、
而且不會有人發現——因為漂移不報錯。

### 四層，各有唯一職責

| 層 | 存什麼 | 可變性 | 由誰決定內容 |
|---|---|---|---|
| `drivers/<slug>.yaml` | 多檔共用、不屬於任何單一標的的變數 | 原地修改 | 跨標的的事實 |
| `state/<ticker>.yaml` | 該標的專屬的論點、情境、變數、否證點 | 原地修改 | 單一標的 |
| `notes/YYYY-MM.md` | 還不成熟、尚未歸屬的觀察 | append-only 收件匣 | 未定 |
| `reports/YYYY/MM/*.md` | 推論記錄與變更單 | **不可變**，錯了寫新的並 `supersedes` | 時間 |

現有 driver：`hyperscaler-capex`（四大 CSP 支出**承諾**）、
`ai-accelerator-demand`（加速器**實際出貨**與 guidance）、
`accelerator-roadmap`（平台**時程與功率密度**）。

### 分流：拿到一則資訊先問三個問題

1. **這個事實會被兩檔以上引用嗎？** 會 → `drivers/`，個股用 `driver_refs` 引用。
2. **它只決定一檔的論點嗎？** 是 → `state/<ticker>.yaml` 的 `key_variables`。
3. **兩個都答不出來？** → `notes/`。收件匣的價值在於門檻低，硬歸類比不歸類糟。

**一個共用事實只能有一個家。**四大 CSP capex 住在 `drivers/hyperscaler-capex.yaml`，
個股引用它，**絕不複製數值進 state**。你若在個股 state 裡看到一個共用數字，
那不是備份，那是即將發生的分歧。

### 讀取順序與優先權

推論前：**先讀 state**（知道這檔在乎哪些變數）→ **再依 `driver_refs` 讀 driver**
（取共用數值的現值）→ **最後讀 `coverage.yaml`**（共同前提是否鬆動）。

**共用數值一律以 driver 為準。** 若 state 裡出現與 driver 重複且不一致的數字，
那是架構錯誤，修的是 state，不是 driver——而且要在報告裡說出來，因為它代表
某一次更新漏了扇出。（現成例子：`state/MSFT.yaml` 的 `driver_refs.note` 記錄了
driver 的 Microsoft 成分 190 與公司揭露的約 175 不符，並註明差額來自會計年限口徑
而非需求下修。這種註記是對的做法——發現不一致時標記它，不要就地改一個數字了事。）

### 來源階層（同一事實有多個來源時的優先順序）

| 順位 | 來源 | 可標的最高 tier |
|---|---|---|
| 1 | 一手官方：財報、10-K／10-Q、法說逐字稿、公司新聞稿、公開資訊觀測站 | 事實 |
| 2 | 一手非官方：OCP／JEDEC 規格文件、監理與法院文件、政府統計 | 事實 |
| 3 | 第三方彙整統計（多來源一致，成分已確認） | **推論**，不可標事實 |
| 4 | 賣方預估／市場共識 | **推論**，須註明機構與報告日期 |
| 5 | 媒體轉述 | 線索而已。必須回溯一手；回溯不到就標「單一二手」並列進 `gaps` |
| 6 | 你記憶中的數字 | **不是來源。** 需要現價、月營收、財報數字就去查 |

順位 3 以下的值**不得單獨支撐 L2 以上的模型變動**。若一次升級的唯一依據是賣方預估，
那不是 L2，是「等一手資料出來再說」。

台股（3324、6442）：**月營收（每月 10 日前）是最高頻的一手數據，優先度高於任何新聞。**

### 收錄與推論分離

`/brief` 只做**共用資料收錄**：更新 driver 層、產生 `drivers/_queue.yaml` 扇出待辦，
不碰任何 `state/`、不寫個股報告。`/cta` 才做**個股推論**。

分開的理由是節奏不同：收錄要每天做、要快；推論貴、要挑值得的做。綁在一起的結果
一定是其中一個被犧牲，而被犧牲的永遠是收錄——然後所有推論都在用過期的數字。

處理個股事件時，**先看 `drivers/_queue.yaml` 有沒有這檔的待辦**，一併處理掉。

## 工作流程

### 1. 定位標的、讀取 state 與 driver
從事件內容判斷影響哪些標的（可能不只一支 — 一則 CoWoS 擴產新聞同時影響 TSM 與 3324）。讀取每個受影響標的的 `state/<ticker>.yaml`。若事件涉及整體 AI capex 或總經，一併讀 `state/coverage.yaml`。

依該檔的 `driver_refs` 讀取對應的 `drivers/<slug>.yaml`，共用數值取那裡的現值，不要用 state 裡的複本（正常情況下也不該有複本）。同時檢查 `drivers/_queue.yaml` 是否已有這檔的待辦——若有，一併處理，處理完移進 `done`。

若標的不在追蹤清單，先問使用者要不要建檔，不要逕自開新檔。

### 2. 影響掃描（先掃描，後定級）
逐一比對事件內容與該檔的 `key_variables` 與 `falsifiers`，列出：
- 觸及了哪些變數？該變數的舊值、事件隱含的新值
- 是否觸及任何否證點？
- 這是新事實，還是既有假設的重述？（很多新聞只是把 base case 再講一次）

掃描完才有辦法定級。反過來先定級再找理由會系統性低估影響。

### 3. 定級（客觀門檻，不憑感覺）

| 等級 | 判定條件（滿足任一即升級） | 必須做的分析深度 |
|---|---|---|
| **L0 噪音** | 未改變任何 key_variable 的數值或信心；已在 base case 假設內；純二手轉述無新增一手事實 | 寫入 `event_log`，說明為何不動模型（兩行） |
| **L1 微調** | 改變 1 個 key_variable；三情境機率變動 < 5pp；目標價變動 < 5% | 更新該變數 + 連動 EPS；出變更單 |
| **L2 重算** | 情境機率變動 ≥ 5pp／目標價變動 ≥ 5%／新增或移除 key_variable／CTA 位階改變（破或站上關鍵均線、量價背離、右側確認成立） | 重跑三情境 EPS 與 DCF、重算目標價、重評訊號；出變更單 + 重生 dashboard |
| **L3 論點層** | 觸發任一 `falsifiers`／thesis 核心前提被推翻／訊號評級需跨級變動（如偏多→偏空） | 跑完整否證清單、重寫 thesis、給明確動作；出全量報告 |

定級後在變更單開頭明寫等級與觸發條件，讓使用者可以檢驗你有沒有偷懶或反應過度。

### 4. 修正模型
只動被事件觸及的變數。未觸及的欄位保持原值，並保留其 `updated` 日期 — 讓陳舊變數自己浮出來（超過 90 天未更新的變數，在變更單結尾以「⚠ 陳舊變數」列出）。

情境機率調整必須寫出**理由與幅度**（例：`base 0.55 → 0.60，+5pp，因液冷滲透率上緣獲客戶端證實`）。三情境機率合計恆為 1.00。

### 5. 產出與回寫
依等級套用 `references/report-templates.md` 的對應模板。輸出變更單後，**一定要**把更新後的 state 以 YAML 區塊呈現（或直接寫檔），並附 diff 摘要，讓使用者能貼回檔案。沒有回寫 state 的變更單等於白做 — 下一則事件又要從頭建 context。

## 證據分層

每個變數值都標 tier，這決定它能承受多少推論重量：

- **事實** — 公司揭露、財報、官方公告、可查證的第三方數據。註明來源與日期。
- **推論** — 由事實經明確邏輯推導。要寫出推導鏈。
- **假設** — 無直接證據支撐的預設值。必須註明，且不可作為升級到 L2/L3 的唯一依據。
- **缺口** — 該知道但目前不知道。列進 `gaps`，並在變更單指出取得途徑（法說 Q&A、月營收、供應鏈查證）。

寧可標「缺口」也不要填一個看起來合理的數字。編造的精確度比誠實的空白危險得多。

## 台股 vs 美股的處理差異

- **台股（3324、6442）**：月營收（每月 10 日前）是最高頻的一手數據，優先度高於新聞。留意除權息造成的價格跳空會影響技術位階判讀。融資融券與三大法人買賣超納入籌碼面。漲跌色慣例為紅漲綠跌。
- **美股（TSM ADR、MSFT、GOOG、META、INTU）**：以季報 + guidance + 財報電話會議為主要節點。guidance 的變動通常比當季實際數字更重要。TSM 同時有 ADR 與台股本體，注意你在講哪一個，以及月營收（台股揭露）對 ADR 的領先性。
- **INTU 屬 AI 應用端／SaaS**，不在 AI capex 硬體鏈上。不要把 capex 相關事件的影響套到它身上 — 它在組合裡的作用正是與 capex 因子低相關。

## 零倉位資訊（最重要的規則）

這是完全公開的倉庫，不含任何倉位資訊。寫任何內容前問：這行能不能被拿來推論持倉？

| 可以寫 | 不可以寫 |
|---|---|
| 論點、情境機率、目標價、EPS 假設 | 成本、張數、配置比重 |
| 否證點、檢驗點、缺口 | Kelly edge / odds / 建議權重 |
| CTA 位階、支撐壓力、技術面失效價位 | 「我的持倉」「作者持有」 |
| 訊號評級（偏多／中性／偏空） | 加碼、減碼、建倉、平倉、進場、出場 |

**訊號不等於動作。** 「偏多」是研究結論；「加碼」是持倉動作，暗示已有部位。永遠用前者。
技術面用 `invalidation`（失效價位），不用「停損」——後者暗示持倉。

報告的「訊號」一節只給評級、信心度、翻轉條件。不給尺寸建議，不寫「建議配置多少」。

`state/coverage.yaml` 是研究覆蓋清單，不是投資組合；因子分析以等權為基準。

寫完跑 `python scripts/check_public.py`。它是正則比對不是理解，最後一道防線是你自己逐句檢查。

## Guardrails

- **不編造數字。** 沒有的值標 `__` 並列進 `gaps`。目標價、EPS、機率都要能追溯到 state 裡的假設。
- **成本基礎不參與估值判斷。** `cost_basis` 只用於計算損益與部位，絕不影響三情境機率或目標價。看到自己在替套牢部位找理由時，那就是 L3。
- **因子集中度示警**：若事件加深覆蓋清單既有的因子集中（如再度強化 AI capex 依賴），在變更單指出，並對照 `state/coverage.yaml` 的 `common_premise`。
- **訊號升級為偏多需右側確認。** 基本面轉好但技術面未確認 → 訊號維持中性，並寫明「等 X 條件成立才翻多」。這是 CTA 紀律的核心，不可因為論點很有說服力就跳過。
- **機率不因價格波動而調整。** 股價漲跌本身不是新資訊，除非它構成 CTA 位階的變化（那是技術面事件，走 L2）。
- **一則事件影響多支個股時，分別出變更單**，不要合併成一篇。但在結尾加一段組合層影響（相關性是否上升、單一因子曝險是否惡化）。
- **需要即時價格、月營收、財報數字時就去查。** 不要用記憶中的數字充當現值。查到後標來源與日期。

## 完成檢查

送出前確認：
1. 等級與觸發條件已明寫
2. 每個變動的變數都有前後值對照與 tier
3. 三情境機率合計 = 1.00
4. 動作建議有明確的觸發條件或價格區間，不是「可留意」這種空話
5. 更新後的 state（含 `last_updated`）已附上
6. 陳舊變數（>90 天）與缺口已列出
