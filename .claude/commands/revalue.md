argument-hint: <ticker>
---

對 $ARGUMENTS 做全量重估。

**這個指令存在的理由**：`/cta` 是事件驅動的，沒有新消息就不會觸發。但估值模型會**因時間經過而失效**，即使什麼事都沒發生——年度滾動（市場從看今年 EPS 轉為看明年）、PE band 位移、股價漂移到情境邊緣、變數過期。這些都不會產生「新聞」，所以需要手動或定期觸發。

建議節奏：每季財報後一次，或當 `validate_state.py --stale` 顯示該檔有變數超過 90 天未更新時。

## 步驟

1. 讀 `state/<ticker>.yaml`，記下現有的 `scenarios`、`weighted_tp`、`signal`、`key_variables` 與各自的 `updated` 日期。

2. **查最新資料**，逐項標來源與日期：
   - 現價、成交量、技術位階（均線、支撐壓力）
   - 最近一季財報：營收、毛利率、EPS
   - 台股另查最近 3 個月月營收與 YoY
   - 市場一致預估 EPS（本年與次年），註明機構與報告日期 → tier 標 `推論`
   - 查不到的標 `缺口`，**不要用推估值填**

3. **檢查估值基準年是否該滾動**。若已進入下半年，市場通常改看次年 EPS。基準年一換，目標價會跳動但那不是新資訊——在報告裡明確標示「基準年由 20XX 改為 20XX」，避免把換基準誤讀成重評價。

4. **重跑三情境**。每個情境寫出：EPS 假設、exit multiple、依據。機率合計必須為 1.00，且要寫 `p_basis`——為何是這個機率。

5. 計算機率加權目標價，與前值比較：
   - 變動 < 5% → 標為 **L1**，只更新 state 與變數日期
   - 變動 ≥ 5% → 標為 **L2**，寫完整重估報告 + 重生 dashboard
   - 若三情境的敘事已與 `thesis` 不符 → **L3**，觸發論點重審

6. **重評訊號**。`signal.rating` 只有偏多／中性／偏空。升級為偏多需右側技術確認——基本面再強、目標價再高，技術面未確認就維持中性並寫明等什麼條件。

7. 檢查 `falsifiers` 是否仍可驗證：門檻還有 `__` 的要補上數字，已過期的 `check_by` 要更新或標為已驗證。

8. 寫報告到 `reports/YYYY/MM/YYYY-MM-DD-<ticker>-revaluation.md`，front-matter 的 `level` 依第 5 步結果填。

   - **同日重跑**：若該檔名已存在，改用 `-revaluation-2`、`-3`。**絕不覆蓋**，
     `check_append_only.py` 會擋下覆蓋行為。
   - **`supersedes`** 填上一份該標的估值報告的路徑，讓索引把舊的標為「已取代」。
     舊報告本身不動 — 讀者從索引就知道它已非現行判斷。
   - L1（變動 < 5%）**不寫報告**，只更新 state 的變數與 `updated` 日期。
     沒有實質變化的報告是雜訊，會稀釋索引的訊噪比。

9. 更新 `state/<ticker>.yaml`，追加 `event_log` 一筆（`summary: 手動重估`），更新 `last_updated`。

10. 跑 `python scripts/check_public.py && python scripts/validate_state.py && python scripts/build_index.py`，然後 commit：`revalue(<ticker>): 加權目標價 X → Y（±Z%）`。

## 注意

**重估不是找理由支持現有評級。** 若重跑後目標價下修但你發現自己在調高 exit multiple 來維持結論，那就是論點漂移——停下來，標 L3。

**情境機率是使用者的判斷，不是我的。** 我可以提供事實、市場預估、計算，以及機率變動的邏輯依據，但機率本身應由使用者決定。若使用者沒指定，用現有值並在報告中標示「機率沿用前值，未重評」。
